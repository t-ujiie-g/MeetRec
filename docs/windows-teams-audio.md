# Windows の Teams の相手の音：調査の手引き

Windows の実機で調べる人（と AI エージェント）向け。経緯は [DECISIONS.md](../DECISIONS.md) の D36、
今の状態は [PROGRESS.md](../PROGRESS.md) の「既知の問題」。

## 困っていること

Windows の Teams だけ、相手の音を「PC から出る音すべて」として録っている（D36）。この方式は **PC の音を消していると無音になる**。
会議室で、ミュートしている人の PC の音を消して使う場面で録れない。

理想は、Zoom と同じく **Teams の音だけ** を、PC の音量や消音に関係なく録れること。

## 分かっていること（2026-11-22、実機のログ・録画・診断ログ）

- Zoom は、アプリの音だけを録る方式（プロセスループバック。`crates/platform-win/src/audio.rs` の `process_loopback_once`）で録れる。
  PC の音を消していても録れた（利用者の確認）。
- Teams に同じ方式を使うと、エラーなく始まり、データも届くが、中身が完全な無音になる。
  - 対象はルートの `ms-teams.exe`、`PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE`。
  - 診断ログでは、出力のオーディオセッションが動作中なのは、ルートの子の `ms-teams.exe`（親 PID はルート）。2 つある。
    `msedgewebview2.exe` にも出力のセッションがあるが動作していない。
  - 子の `ms-teams.exe` を直接の対象にしても無音だった（利用者の確認。そのときのログと録画は残っていない）。
- 出力機器のループバック（`system_loopback_once`）なら、イヤホンをつないで音を出している状態で録れた。PC の音を消すと無音。
  「消した」のが Windows 全体の消音か、Teams の中のスピーカーのオフかは未確認。
- OBS の Application Audio Capture でも、新しい Teams の音が録れないという報告がある（原因の説明は見つかっていない）。

## 確かめたいこと（優先順）

結果は、PROGRESS.md の「実機で確認できたこと」か「既知の問題」に書き足す。

1. **消音の種類ごとの違い**（数分で終わる。運用で避けられるかが決まる）
   - Windows の音量を 1〜2% にする（消音にはしない）→ 録れるか。
   - タスクバーのスピーカーを消音にする → 録れるか。
   - 音量ミキサーで Teams だけを消す → 録れるか。
   - Teams の中でスピーカーをオフにする／出力先を変える → 録れるか（録れなくて当然だが、どう見えるかを確かめる）。
   - 出力先を、音が鳴らない別の出力機器（モニターの音声出力など）にする → 録れるか。
2. **プロセスループバックが Teams で無音になる条件**
   - 対象の PID を 1 つずつ変える：ルート、子の `ms-teams.exe`、各 `msedgewebview2.exe`。子プロセスを含める／含めないの両方。
   - `PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE` で、関係のないプロセス（MeetRec 自身）を除外対象にする
     （＝それ以外すべてを録る）。Teams の音が入るか。入れば、消音の影響を受けるかも確かめる。
   - 取り込みを始める時機：通話が始まる前と、相手が話している最中とで違うか。
   - MeetRec を管理者として実行した場合に変わるか（OBS のフォーラムにそういう助言があった。配布形態としては採れないが、原因の手がかりになる）。
   - Teams の設定で変わるか：出力機器の選び方、空間オーディオ、ノイズ抑制、ハードウェア アクセラレーション。
3. **Teams の音の出し方の特徴**
   - 子の `ms-teams.exe` のセッションが、どの出力機器（既定／通信用）にあるか、ストリームのカテゴリは何か。
   - Teams がパッケージ アプリ（MSIX）であることや、プロセスの整合性レベルが関係するか。
   - Microsoft のサンプル（Windows-classic-samples の ApplicationLoopback）で同じ PID を録って、同じく無音になるか。
     なるなら MeetRec の実装の問題ではない。

## 調べるための道具

- `MeetRec.exe` の「診断ログを保存」：出力側のオーディオセッション（プロセス・親・動作中か）が出る（`probe.rs` の `diagnostics`）。
- `%APPDATA%\MeetRec\meetrec.log`：「相手音声のキャプチャ開始（…）」に、どの方式で始めたかが出る。
- 方式の切り替え：`config.toml` の `[[app]]` で `id = "teams"` の定義を丸ごと書けば、`system_audio = false` にして
  プロセスループバックを試せる（組み込みの定義は `crates/core/src/rules/builtin.rs`。診断ログの「有効な会議アプリ定義」を
  写して書き換えるのが早い）。
- 実験用に PID や方式を変えたいときは、`audio.rs` を一時的に書き換えてビルドする（`cargo build --release -p meetrec`。
  できた `target\release\meetrec.exe` をそのまま起動できる。先にインストール済みの MeetRec を終了すること）。
- 録れたかどうかは、自分を Teams でミュートにして録り、録画の音量で判定するのが確実（自分のマイクが止まるので、残る音は相手の音だけ）。
  `ffmpeg -i 録画.mp4 -vn -af volumedetect -f null -` の `mean_volume` が `-91 dB` 付近なら無音。

## 守ること

- 実験で分かった事実と、推測を分けて書く。録れた・録れないは、ログと録画の音量で確かめてから書く。
- 直せた場合も、Zoom の経路（録れている）は変えない。会議アプリごとの違いは `rules/builtin.rs` の表に書く（AGENTS.md）。
- 仮想オーディオ デバイス（ドライバーの導入が要るもの）は、方針（軽量・導入が簡単）に合わないので、採る前に利用者に確認する。
